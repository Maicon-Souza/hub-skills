# Design de tabelas no PostgreSQL

Referência para projetar tabelas no PostgreSQL. Explique em português do Brasil; mantenha em inglês os comandos SQL, nomes de tipos e funções. Nomes de tabelas e colunas seguem o padrão do projeto (em português ou inglês, sempre em `snake_case`).

## Regras principais

- **Chave primária** em tabelas de referência (usuários, pedidos etc.). Nem sempre é necessária em dados de série temporal, eventos ou logs. Quando usar, prefira `BIGINT GENERATED ALWAYS AS IDENTITY`; use `UUID` só quando precisar de unicidade global ou de um ID opaco.
- **Normalize primeiro (até a 3FN)** para eliminar redundância e anomalias de atualização. Desnormalize **só** quando a leitura for comprovadamente lenta por causa dos joins e o ganho for medido. Desnormalizar cedo demais cria custo de manutenção.
- **NOT NULL** em toda coluna que semanticamente não pode ser vazia; **DEFAULT** para valores comuns.
- **Índices para as consultas que você realmente faz:** chave primária e UNIQUE (automáticos), **colunas de chave estrangeira (manual!)**, filtros e ordenações frequentes e chaves de join.
- Prefira **TIMESTAMPTZ** para data e hora de eventos, **NUMERIC** para dinheiro, **TEXT** para textos, **BIGINT** para inteiros e **DOUBLE PRECISION** para números de ponto flutuante (ou `NUMERIC` para aritmética decimal exata).

## Pegadinhas do PostgreSQL

- **Identificadores:** sem aspas, viram minúsculas. Evite nomes entre aspas ou com maiúsculas. Convenção: `snake_case` para tabelas e colunas.
- **UNIQUE e NULL:** UNIQUE permite vários NULLs. Para aceitar só um, use `UNIQUE NULLS NOT DISTINCT (col1, col2)` (PostgreSQL 15+).
- **Índice em chave estrangeira:** o PostgreSQL **não** cria índice automático nas colunas de FK. Crie.
- **Sem conversão silenciosa:** estouro de tamanho ou precisão dá erro, não trunca. Exemplo: inserir 999 em `NUMERIC(2,0)` falha, ao contrário de bancos que arredondam ou cortam em silêncio.
- **Sequências e identity têm buracos** (normal; não "conserte"). Rollbacks, quedas e transações concorrentes geram saltos nos IDs (1, 2, 5, 6...). Não tente deixar os IDs consecutivos.
- **Armazenamento em heap:** não há chave primária clusterizada por padrão (diferente do SQL Server e do InnoDB do MySQL). `CLUSTER` reorganiza uma vez só e não se mantém nas inserções seguintes. A ordem no disco é a de inserção, salvo `CLUSTER`.
- **MVCC:** updates e deletes deixam versões mortas das linhas, que o vacuum limpa. Evite projetar tabelas com linhas largas atualizadas o tempo todo.

## Tipos de dados

- **IDs:** `BIGINT GENERATED ALWAYS AS IDENTITY` de preferência (`GENERATED BY DEFAULT` também serve); `UUID` para sistemas distribuídos, junção de bases ou IDs opacos. Gere com `uuidv7()` (PostgreSQL 18+, ordenável por tempo, melhor para índices) ou `gen_random_uuid()` (nativo desde o PostgreSQL 13, sem extensão).
- **Inteiros:** prefira `BIGINT`, a menos que espaço seja crítico; `INTEGER` para faixas menores; evite `SMALLINT` salvo restrição real.
- **Ponto flutuante:** `DOUBLE PRECISION` em vez de `REAL`, salvo quando espaço for crítico. `NUMERIC` para aritmética decimal exata.
- **Textos:** prefira `TEXT`; para limitar tamanho, use `CHECK (length(col) <= n)` em vez de `VARCHAR(n)`; evite `CHAR(n)`. `BYTEA` para binários. Valores grandes (acima de cerca de 2 KB) vão automaticamente para o TOAST, com compressão; o padrão (`EXTENDED`) costuma ser o melhor. Para comparar sem diferenciar maiúsculas e minúsculas: índice de expressão em `lower(col)` (preferido, a menos que a coluna precise de PK, FK ou UNIQUE sem diferenciação) ou `CITEXT`; para ignorar acentos e regras de idioma, collations não determinísticas ou a extensão `unaccent`.
- **Documentos brasileiros:** CPF, CNPJ, CEP e telefone são **texto**, não número: zeros à esquerda se perdem em colunas numéricas. Exemplo: `cpf TEXT CHECK (cpf ~ '^[0-9]{11}$')`. Valide os dígitos verificadores na aplicação ou numa função. O CNPJ passará a ter letras a partir de julho de 2026 (CNPJ alfanumérico); não use regex só de dígitos para CNPJ.
- **Dinheiro:** `NUMERIC(p,s)` (nunca ponto flutuante).
- **Datas e horas:** `TIMESTAMPTZ` para data e hora; `DATE` só para data; `INTERVAL` para durações. Evite `TIMESTAMP` sem fuso. `now()` retorna o início da transação; `clock_timestamp()`, a hora atual de verdade. Guarde em `TIMESTAMPTZ` e converta para `America/Sao_Paulo` (ou o fuso do usuário) na exibição.
- **Booleanos:** `BOOLEAN NOT NULL`, a menos que três estados sejam necessários.
- **Enums:** `CREATE TYPE ... AS ENUM` para conjuntos pequenos e estáveis (ex.: dias da semana, UFs). Para valores de regra de negócio que mudam (ex.: status de pedido), use TEXT com CHECK ou uma tabela de referência.
- **Arrays:** `TEXT[]`, `INTEGER[]` etc., para listas ordenadas consultadas por elemento. Índice **GIN** para contém (`@>`, `<@`) e sobreposição (`&&`). Acesso: `arr[1]` (começa em 1), `arr[1:3]`. Bons para tags e categorias; para relações, use tabela de ligação. Literais: `'{a,b}'` ou `ARRAY[a, b]`.
- **Intervalos (range):** `daterange`, `numrange`, `tstzrange`, com operadores de sobreposição (`&&`) e contém (`@>`). Índice **GiST**. Bons para agendas, versões e faixas. Use um padrão de limites e mantenha; de preferência `[)` (inclui o início, exclui o fim).
- **Rede:** `INET` para IPs, `CIDR` para redes, `MACADDR` para endereços MAC, com operadores próprios (`<<`, `>>`, `&&`).
- **Geometria:** `POINT`, `LINE`, `POLYGON`, `CIRCLE` para dados 2D, com índice **GiST**. Para geografia de verdade, use **PostGIS**.
- **Busca textual:** `TSVECTOR` para documentos e `TSQUERY` para consultas, com índice **GIN**. Sempre informe o idioma, no índice e na consulta: `to_tsvector('portuguese', col)` e `to_tsquery('portuguese', 'termo')`. Nunca use as versões de um argumento. Para ignorar acentos, crie uma configuração de busca com `unaccent`.
- **Domínios:** `CREATE DOMAIN email AS TEXT CHECK (VALUE ~ '^[^@]+@[^@]+$')` para tipos reutilizáveis com validação.
- **Tipos compostos:** `CREATE TYPE endereco AS (logradouro TEXT, cidade TEXT, cep TEXT)`; acesso com `(col).campo`.
- **JSONB:** preferível a JSON, com índice **GIN**. Use só para atributos opcionais ou semiestruturados. Use JSON apenas se a ordem original das chaves precisar ser preservada.
- **Vetores:** tipo `vector` da extensão `pgvector`, para busca por similaridade de embeddings.

### Tipos a evitar

- `timestamp` (sem fuso): use `timestamptz`.
- `char(n)` e `varchar(n)`: use `text` (com CHECK, se precisar limitar).
- `money`: use `numeric`.
- `timetz`: use `timestamptz`.
- `timestamptz(0)` ou outra precisão: use `timestamptz`.
- `serial`: use `generated always as identity`.

## Tipos de tabela

- **Comum:** padrão; durável e registrada no log (WAL).
- **TEMPORARY:** existe só na sessão, é apagada no fim e não vai para o log. Mais rápida para trabalho temporário.
- **UNLOGGED:** persistente, mas perde os dados numa queda do servidor e não é replicada. Escrita mais rápida; boa para cache e área de preparação.

## Segurança por linha (RLS)

Ative com `ALTER TABLE tbl ENABLE ROW LEVEL SECURITY` e crie políticas. Exemplo, com o ID do usuário passado pela aplicação numa configuração de sessão:

```sql
ALTER TABLE pedidos ENABLE ROW LEVEL SECURITY;

CREATE POLICY pedidos_do_usuario ON pedidos
  FOR SELECT TO app_usuarios
  USING (usuario_id = current_setting('app.usuario_id')::bigint);
```

O dono da tabela ignora as políticas, a menos que você use `ALTER TABLE ... FORCE ROW LEVEL SECURITY`; superusuários e papéis com `BYPASSRLS` sempre ignoram. A aplicação deve se conectar com um papel comum. RLS ajuda a cumprir a LGPD ao limitar quem vê dados pessoais, junto com controle de acesso e auditoria (`pgaudit`).

## Restrições

- **Chave primária:** UNIQUE + NOT NULL implícitos; cria índice B-tree.
- **Chave estrangeira:** defina a ação de `ON DELETE`/`ON UPDATE` (`CASCADE`, `RESTRICT`, `SET NULL`, `SET DEFAULT`). Crie índice na coluna que referencia: acelera joins e evita bloqueios e varreduras ao apagar ou alterar a linha-pai. Use `DEFERRABLE INITIALLY DEFERRED` para dependências circulares, verificadas no fim da transação.
- **UNIQUE:** cria índice B-tree; aceita vários NULLs, salvo com `NULLS NOT DISTINCT` (PostgreSQL 15+). Por padrão, `(1, NULL)` pode se repetir; com `NULLS NOT DISTINCT`, só uma vez. Prefira `NULLS NOT DISTINCT`, a menos que precise de NULLs repetidos.
- **CHECK:** regras dentro da linha; NULL passa na verificação (lógica de três valores). `CHECK (preco > 0)` aceita preço NULL. Combine com NOT NULL: `preco NUMERIC NOT NULL CHECK (preco > 0)`.
- **EXCLUDE:** impede valores sobrepostos. `EXCLUDE USING gist (sala_id WITH =, periodo WITH &&)` impede reservar a mesma sala duas vezes no mesmo período. Para usar `=` com inteiros num índice GiST, ative antes a extensão `btree_gist`.

## Índices

- **B-tree:** padrão, para igualdade e faixas (`=`, `<`, `>`, `BETWEEN`, `ORDER BY`).
- **Composto:** a ordem importa. O índice é usado quando há filtro na parte inicial: `WHERE a = ? AND b > ?` usa o índice `(a, b)`; `WHERE b = ?` normalmente não. Coloque primeiro as colunas filtradas por igualdade e depois as de faixa ou ordenação.
- **Cobertura (INCLUDE):** `CREATE INDEX ON tbl (id) INCLUDE (nome, email)` guarda colunas extras no índice para leituras sem visitar a tabela (index-only scan).
- **Parcial:** para subconjuntos muito consultados. `CREATE INDEX ON tbl (usuario_id) WHERE status = 'ativo'` serve às consultas que também filtram `status = 'ativo'`.
- **Expressão:** para chaves calculadas, como `CREATE INDEX ON tbl (lower(email))`. A consulta precisa usar exatamente a mesma expressão: `WHERE lower(email) = 'usuario@exemplo.com'`.
- **GIN:** JSONB (contém e existência de chave), arrays (`@>`, `?`) e busca textual (`@@`).
- **GiST:** intervalos, geometria e restrições EXCLUDE.
- **BRIN:** tabelas enormes com dados naturalmente ordenados (séries temporais), com espaço mínimo. Funciona quando a ordem física acompanha a coluna indexada.

## Particionamento

- Para tabelas muito grandes (centenas de milhões de linhas) em que as consultas quase sempre filtram pela chave de partição (geralmente data).
- Também quando a manutenção pede: dados apagados ou substituídos em bloco periodicamente (apagar uma partição é instantâneo).
- **RANGE:** comum para séries temporais (`PARTITION BY RANGE (criado_em)`). Exemplo: `CREATE TABLE logs_2026_01 PARTITION OF logs FOR VALUES FROM ('2026-01-01') TO ('2026-02-01')`. A extensão **TimescaleDB** automatiza o particionamento por tempo, com retenção e compressão.
- **LIST:** valores discretos (`PARTITION BY LIST (regiao)`), como `FOR VALUES IN ('sudeste', 'sul')`.
- **HASH:** distribuição uniforme quando não há chave natural (`PARTITION BY HASH (usuario_id)`).
- **Poda de partições:** no particionamento declarativo, o planejador descarta automaticamente as partições fora do filtro (partition pruning); não é preciso criar CHECKs à mão.
- Use particionamento declarativo (ou hypertables do TimescaleDB). **Não** use herança de tabelas.
- **Limitações:** não há UNIQUE global; a chave de partição precisa fazer parte da chave primária e dos UNIQUE. Chaves estrangeiras **são** suportadas: de tabelas particionadas desde o PostgreSQL 11 e apontando para tabelas particionadas desde o 12.

## Situações especiais

### Tabelas com muitas atualizações
- **Separe colunas quentes e frias:** colunas atualizadas o tempo todo numa tabela separada, para reduzir o inchaço.
- **`fillfactor = 90`** (ou menor) para deixar espaço para atualizações HOT, que evitam mexer nos índices.
- **Evite atualizar colunas indexadas:** isso impede as atualizações HOT.
- **Particione pelo padrão de atualização:** linhas muito atualizadas numa partição, dados estáveis em outra.

### Tabelas com muitas inserções
- **Poucos índices:** só os que você consulta; cada índice deixa a inserção mais lenta.
- **`COPY` ou `INSERT` de várias linhas** em vez de uma linha por vez.
- **Tabelas UNLOGGED** para dados de preparação que podem ser reconstruídos.
- **Cargas em massa:** apague os índices, carregue e recrie os índices depois.
- **Particione por tempo ou hash** para distribuir a carga. O TimescaleDB automatiza particionamento e compressão.
- **Chave natural** como `(registrado_em, dispositivo_id)` quando a unicidade importar; muitas tabelas de inserção intensa nem precisam de chave primária.
- Se precisar de chave artificial, prefira `BIGINT GENERATED ALWAYS AS IDENTITY` a `UUID` aleatório (ou use `uuidv7()`, que é ordenado por tempo).

### Upsert (`INSERT ... ON CONFLICT`)
- **Precisa de índice ou restrição UNIQUE** exatamente nas colunas de conflito. Índices únicos parciais também servem, desde que a cláusula repita o predicado: `ON CONFLICT (col) WHERE ativo`.
- **`EXCLUDED.coluna`** referencia o valor que seria inserido; atualize só as colunas que mudam, para reduzir escrita.
- **`DO NOTHING`** é mais rápido que `DO UPDATE` quando não é preciso atualizar.

### Evolução segura do schema
- **DDL transacional:** a maioria dos comandos DDL roda dentro de transação e pode ser desfeita: `BEGIN; ALTER TABLE ...; ROLLBACK;` para testar com segurança.
- **Índice sem bloquear escrita:** `CREATE INDEX CONCURRENTLY`, que não roda dentro de transação. Se falhar, deixa um índice inválido para apagar e recriar.
- **Default volátil reescreve a tabela:** adicionar coluna com default volátil (`clock_timestamp()`, `gen_random_uuid()`, `random()`) reescreve a tabela inteira. Defaults constantes (e `now()`, que é estável) são instantâneos desde o PostgreSQL 11.
- **NOT NULL em tabela grande:** crie antes um `CHECK (col IS NOT NULL) NOT VALID`, valide com `VALIDATE CONSTRAINT` e só então aplique `SET NOT NULL`, evitando um bloqueio longo.
- **Apague restrições antes das colunas:** `ALTER TABLE ... DROP CONSTRAINT` e depois `DROP COLUMN`, para evitar problemas de dependência.
- **Funções:** `CREATE OR REPLACE` com argumentos diferentes cria uma sobrecarga, não substitui. Apague a versão antiga se não quiser as duas.

## Colunas geradas

`... GENERATED ALWAYS AS (<expressão>) STORED` para campos calculados e indexáveis. O PostgreSQL 18 adiciona colunas `VIRTUAL` (calculadas na leitura, sem armazenamento), que passam a ser o padrão quando não se informa o tipo.

## Extensões

- **`pgcrypto`:** funções de criptografia, como `crypt()` para hash de senhas. Em geral, é melhor fazer o hash de senhas na aplicação (Argon2 ou bcrypt), para a senha em texto puro nunca chegar ao banco nem aos logs.
- **`uuid-ossp`:** desnecessária em projetos novos; `gen_random_uuid()` é nativo desde o PostgreSQL 13 e `uuidv7()` desde o 18.
- **`pg_trgm`:** busca aproximada com o operador `%` e a função `similarity()`. Com índice GIN, acelera `LIKE '%termo%'`.
- **`unaccent`:** remove acentos para busca ("josé" encontra "jose").
- **`citext`:** texto sem diferenciar maiúsculas e minúsculas. Prefira índice de expressão em `lower(col)`, a menos que precise da restrição sem diferenciação.
- **`btree_gin` / `btree_gist`:** classes de operador B-tree em índices GIN e GiST, para índices compostos que misturam tipos comuns com JSONB, arrays ou intervalos (e para EXCLUDE com `=`).
- **`hstore`:** pares chave-valor; quase sempre substituído por JSONB.
- **`timescaledb`:** séries temporais, com particionamento automático, retenção, compressão e agregados contínuos.
- **`postgis`:** suporte geoespacial completo, essencial para aplicações com localização.
- **`pgvector`:** busca por similaridade de embeddings.
- **`pgaudit`:** registro de auditoria da atividade no banco.

## JSONB

- Prefira `JSONB` com índice **GIN**.
- Padrão: `CREATE INDEX ON tbl USING GIN (dados);`, que acelera:
  - contém: `dados @> '{"chave":"valor"}'`;
  - existência de chave: `dados ? 'chave'`, qualquer ou todas as chaves: `?|`, `?&`;
  - contém em documentos aninhados.
- Muitas consultas só de contém (`@>`): use a classe `jsonb_path_ops`, com índice menor e mais rápido: `CREATE INDEX ON tbl USING GIN (dados jsonb_path_ops);`. Em troca, perde o suporte a `?`, `?|` e `?&`.
- Igualdade ou faixa num campo específico: extraia para uma coluna gerada (ou índice de expressão) com B-tree:
  ```sql
  ALTER TABLE tbl ADD COLUMN preco INT GENERATED ALWAYS AS ((dados->>'preco')::int) STORED;
  CREATE INDEX ON tbl (preco);
  ```
  E consulte `WHERE preco BETWEEN 100 AND 500`, que usa o índice.
- Arrays dentro do JSONB: GIN com `@>` (ex.: tags); `jsonb_path_ops` se for só contém.
- Relações principais ficam em tabelas; JSONB é para atributos opcionais ou variáveis.
- Limite o formato com CHECK: `config JSONB NOT NULL CHECK (jsonb_typeof(config) = 'object')`.

## Exemplos

### Usuários

```sql
CREATE TABLE usuarios (
  usuario_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email TEXT NOT NULL,
  nome TEXT NOT NULL,
  cpf TEXT CHECK (cpf ~ '^[0-9]{11}$'),
  criado_em TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX usuarios_email_unico ON usuarios (lower(email));
CREATE UNIQUE INDEX usuarios_cpf_unico ON usuarios (cpf);
CREATE INDEX ON usuarios (criado_em);
```

O UNIQUE em `lower(email)` já impede e-mails repetidos com maiúsculas diferentes; não é preciso um UNIQUE extra na coluna `email`.

### Pedidos

```sql
CREATE TABLE pedidos (
  pedido_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  usuario_id BIGINT NOT NULL REFERENCES usuarios (usuario_id),
  status TEXT NOT NULL DEFAULT 'PENDENTE'
    CHECK (status IN ('PENDENTE', 'PAGO', 'CANCELADO')),
  total NUMERIC(12,2) NOT NULL CHECK (total > 0),
  criado_em TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON pedidos (usuario_id);
CREATE INDEX ON pedidos (criado_em);
```

### JSONB

```sql
CREATE TABLE perfis (
  usuario_id BIGINT PRIMARY KEY REFERENCES usuarios (usuario_id),
  atributos JSONB NOT NULL DEFAULT '{}' CHECK (jsonb_typeof(atributos) = 'object'),
  tema TEXT GENERATED ALWAYS AS (atributos->>'tema') STORED
);
CREATE INDEX perfis_atributos_gin ON perfis USING GIN (atributos);
```

### Reserva sem sobreposição

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE reservas (
  reserva_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sala_id BIGINT NOT NULL,
  periodo TSTZRANGE NOT NULL,
  EXCLUDE USING gist (sala_id WITH =, periodo WITH &&)
);
```

Ao projetar ou revisar tabelas, entregue o SQL completo (`CREATE TABLE`, índices, restrições), uma explicação curta de cada decisão relevante (tipo, chave, índice) e os pontos de atenção: versão mínima do PostgreSQL exigida, extensões necessárias e impactos de migração em tabelas existentes.
